# Аудит задержек, маршрутизации и диагностики — 2026-10-23

Исходная точка: `ea8a5ed6`, ветка `vps_testai`. Проверены исходники и локальные
offline-сценарии. Отчёт не устанавливает состояние production VPS или доступность
внешних API. Текущая инструкция оператора обновлена в
[runtime controls](runtime-controls.md#диагностика-моделей).

## Метод и границы

Работа разделена между субагентами по frontend дэшборда, его backend и маршрутам
провайдеров. После уточнения пользователя все дальнейшие субагенты использовали
`gpt-6.1-sol`, reasoning `xhigh` для логики конкурентности, согласованности
настроек и диагностики. Координатор проверял поиск, кэш, документный контекст,
файловый I/O и мониторинг БД. Изменения дополнительно проверялись перекрёстно.

Статический AST-обход охватил все 290 Python runtime-файлов в `app/` и `bot.py`.
Проверялись прямые синхронные сетевые, subprocess, sleep и файловые вызовы внутри
async-функций, с исключением вложенных синхронных функций. Это проверка конкретных
форм вызовов, а не профилирование всех транзитивных зависимостей. Наиболее подробно
разобраны пользовательские запросы, гонки моделей/ключей, retries, snapshots,
лимиты, отбор контекста и достоверность отображаемых состояний. Остальные domain
сценарии проверяются общим offline-набором; ручное выполнение каждой команды
с реальными сервисами не проводилось.

Все новые сценарии используют искусственные данные, подмену внешнего transport
и offline Chromium. Настоящие `.env`, ключи, сообщения пользователей, документы,
birth data и приватные log archives не читались. Миграции и приложение с реальными
Telegram/provider подключениями не запускались. Dependency graph не изменён.

## Подтверждённые исправления

| Область | Причина | Новое поведение |
| --- | --- | --- |
| Гонка ключей | Второй resolver мог выбрать другую модель и перезаписать модель первого ключа | Сопутствующий ключ ищется для уже выбранной модели |
| Гонки моделей | Ветка с запрещённым fallback всё равно расширяла поиск ключей | Каждая ветка сохраняет свою модель, OpenRouter exact resolver тоже не добавляет fallback |
| Состояние проигравшего ключа | Успешная соседняя ветка скрывала уже полученный quota/invalid failure | Известный отказ сохраняется; одна отмена проигравшей ветки не ухудшает ключ |
| Повторы HTTP | Пустые HTTPX exceptions не распознавались, а текст постоянной HTTP-ошибки мог вызвать повтор | Тип и HTTP status определяют повторяемость раньше текстовых эвристик |
| Подсказки выбора | Устаревшее ранжирование не учитывало текущую primary и путало Flash с Flash Lite | Текущие семейства сопоставляются точно; неизвестная модель не получает недоказанную рекомендацию замены |
| Поисковый кэш | Идентичность не включала `max_results` | Разные лимиты имеют разные записи в Memory и Redis; Q&A сохраняет прежнюю идентичность |
| Пакетный поиск | Одинаковые запросы одновременно обходили пустой кэш | Дубли удаляются до запуска обращений; нулевой итоговый бюджет не вызывает сервис |
| Поисковая выдача | Некорректный score или `results: null` ломал весь merge | Ошибочный score получает ноль, malformed список пропускается, остальные результаты сохраняются |
| Документный контекст | Остановка на неподходящем размере теряла подходящие меньшие фрагменты | После первого выбранного фрагмента рассматриваются последующие помещающиеся фрагменты; лучший слишком большой фрагмент сохраняется усечённым |
| Границы разбиения | Нулевой размер или overlap ≥ 1 могли не продвигать цикл | Некорректные параметры отклоняются; отрицательный context budget не превращается в почти полный документ |
| Локальный Telegram I/O | Метаданные и чтение shared volume выполнялись в event loop | Чтение перенесено в worker; фактически прочитанные байты ограничены и при росте файла |
| Пул PostgreSQL | Монитор и dashboard читали отсутствующие private-поля asyncpg | Публичные методы возвращают размер, idle и реальные предупреждения о загрузке |
| Redis stats | Отчёт всегда читал `db0`, ошибки включали backend detail | Учитывается база подключения; HTTP-ответ не содержит исходную ошибку с возможными credentials |
| Snapshot панели | Один зависший источник удерживал результаты остальных | Каждый источник получает cooperative timeout и безопасный код отказа |
| Snapshot и SSE | SSE мог вернуть зелёную БД по наличию пула после неудачного probe; текст ошибки нарушал JSON | Проверенный snapshot владеет service health, SSE передаёт счётчики и безопасно сериализованную ошибку |
| Лимиты в controls | Холодный запрос выполнял отдельный SELECT на модель и повторно читал baselines | Промахи кэша объединены в один запрос, процессные строки повторно используются из того же GET |
| Состояние ключей | Истёкший cooldown выглядел действующей блокировкой | Отдельно показаны действующее и записанное состояние, покрытие и ограничение выборки |
| Учёт моделей | Completion и API-attempt события имели смешанную область действия, typed streams не имели собственного счётчика попыток | Transport владеет API-попытками, обработчики отдельно учитывают завершённые ответы конкретному пользователю |

Сохранённая ошибка провайдера очищается существующим sanitizer до усечения
для dashboard: обрезание полного credential раньше очистки больше не оставляет
его нераспознаваемый фрагмент. Тест использует только вымышленный credential.

В документном отборе запрос нормализуется один раз, а не для каждого дочернего
фрагмента. Округление token estimate больше не пропускает текст сверх бюджета
на пограничных коротких документах. Независимое ревью дополнительно проверило
сохранение самого релевантного фрагмента при маленьком бюджете.

## Изменения интерфейса

Новый раздел диагностики показывает для каждой модели сохранённые назначения,
локальные RPD-счётчики, допуск по порогу и состояние ключей. Он позволяет искать
модель, фильтровать ограничения и переходить к конкретному процессу.
Порядок провайдеров речи не выдаётся за model ID. Внешний доступ явно остаётся
непроверенным; отсутствие учёта не отображается как нулевой расход.

Snapshot загружается при первом открытии диагностики и переиспользуется при
навигации. Показаны дата учёта, неполное покрытие, разные ревизии и degraded
конфигурация. Неудачное обновление сохраняет предыдущие данные с отметкой
устаревания. Основной dashboard очищает старые детали исчезнувшего источника,
не добавляет отсутствующее CPU-измерение как ноль и отличает локальный порог
от исчерпания полного лимита. Отсутствие ошибок в выборке не объявляется
исправностью всех систем. Вывод model ID и внешних ошибок использует текст.

## Измеренный эффект

- Холодный список трёх лимитов: **3 SELECT → 1 SELECT**. Тест также сохраняет
  `null` overrides, cache и env/DB precedence.
- Гонка моделей в воспроизведённом сценарии: **5 → 3** чтения поиска ключей;
  usable primary больше не заменяется последующей fallback-моделью.
- Пакет `first, first, second, first`: **4 → 2** внешних поиска с сохранением
  порядка независимых результатов.
- Синтетический документ на 104 050 символов: median **2,039 → 1,510 мс**
  на вызов `chunk_for_context`, примерно **26%** меньше локального CPU-времени.
  Сравнение с `git show ea8a5ed6:app/documents/chunking.py`, пять повторов по
  30 вызовов, тот же текст и query. Это микроизмерение данного окружения,
  а не обещание ускорения всей Telegram-операции.

Локальные резервирования RPD не являются биллингом провайдера. Кооперативная
отмена может требовать дополнительного времени для cleanup. Проверка транспорта,
реальной provider latency, реального PostgreSQL/Redis и deployment требует
изолированных сервисов или отдельного эксплуатационного прогона.

Счётчики typed Gemini/Vertex и OpenRouter-compatible transport фиксируют попытки,
дошедшие до SDK/HTTP, включая неудачные и отменённые ветви гонки. Ошибка локальной
валидации не создаёт попытку API. Завершённый chat/photo/document/inline response
относит модель к пользователю без дополнительной API-попытки; неуспешный запрос
не получает такой credit. Другие специализированные SDK consumers сохраняют
свою существующую instrumentation: эти показатели не обещают полный биллинг
всех провайдеров и всех видов операции. Исторические totals не пересчитывались.

## Проверки и артефакты

Среда: Python 3.14.3, uv 0.13.5, Node.js 24.13.0. Локальный uv обновлён до
закреплённой проектом версии; manifests и dependency lock-файлы не менялись.

Новые регрессии запускались до исправлений и воспроизводили дефекты.
Изолированные затронутые наборы прошли: provider/resilience/metrics — 353 теста,
backend/handlers/privacy/auth — 284, поиск/кэш/документы/I/O — 117.
Эти наборы пересекаются, их результаты нельзя складывать в общий pass count.
После финального исправления SSE отдельный объединённый browser/backend набор
прошёл 24 проверки. Browser-случай использует настоящий `EventSource` с искусственным
`text/event-stream`: поздняя подсказка `connected` не заменяет snapshot `unknown`,
а request/queue counters продолжают обновляться.

Перекрёстное ревью обнаружило и помогло исправить два пограничных случая новых
оптимизаций: вытеснение наиболее релевантного фрагмента при маленьком бюджете
и отказ всего пакетного поиска из-за одного нехешируемого элемента provider args.
Отдельно исправлен E2E resolver double, не реализовавший новый exact вызов;
существующие проверки cascade сохранены, последующий затронутый набор — 86 passed.

Ранний serial-прогон завершился с 5142 passed и четырьмя ошибками `inspect.getsource`:
файлы изменились после импорта, и тест читал строки по прежним offsets. Повтор
всех RLS-проверок в новом процессе — 19 passed. Итоговая проверка проведена
после остановки редактирования runtime и tests, чтобы исключить этот конфликт.

Скриншоты и машинный JUnit сохраняются в игнорируемом каталоге
`output/performance-dashboard-audit-2026-10-23/`. Для каждого экрана есть desktop
1366 px и mobile 390 px. Browser tests проверяют отсутствие горизонтального
переполнения, ошибок JS, интерпретации model/error текста как HTML,
работу фильтров, переходов, повторного использования snapshot и статусов отказа.
Изображения содержат только искусственные fixture-данные.
