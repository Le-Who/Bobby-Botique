# Dependency Frontier Validation Design

**Date:** 2026-08-29  
**Status:** Approved for implementation  
**Scope:** Python dependency discovery, reproducible locking, scheduled update proposals, and validation

## Objective

Create a repeatable process that, every 14 days and on demand:

1. discovers newer direct and transitive Python dependencies, including releases hidden by current upper bounds or exact pins;
2. asks a pinned `uv` resolver for one canonical highest compatible graph for Python 3.14 and the production Linux platform;
3. validates candidate graphs with deterministic, integration, container, security, and controlled live-service checks;
4. groups patch and minor updates while isolating major updates unless they must move together;
5. produces durable, evidence-rich reports and pull requests without ever merging automatically.

The process must not claim that dependency metadata resolution or a finite test suite proves complete application compatibility. Its strongest positive result is **validated candidate**, not “proven compatible.”

## Current-State Problems

- `requirements.txt` and `requirements-dev.txt` contain broad ranges and exact pins, while the production Docker build resolves those ranges afresh on every build.
- `uv.lock` contains no dependency graph because dependency metadata is absent from `pyproject.toml`.
- CI checks the current requirements, application tests, and known vulnerabilities, but does not discover releases outside current upper bounds.
- The existing 2,825-test suite mocks external providers by design. It cannot detect every SDK/API integration break against Telegram, Gemini, or Tavily.
- A locally installed environment can drift from repository policy; therefore installed-package inspection is not a valid project-wide source of truth.

## Terminology and Truth Model

### Baseline

The committed `pyproject.toml` plus committed `uv.lock` at the base commit.

### Policy candidate

The newest graph selected by the pinned resolver while preserving all committed direct dependency constraints.

### Frontier candidate

The newest graph selected after removing version specifiers from direct registry dependencies in a temporary input while preserving package names, extras, environment markers, Python 3.14, platform requirements, prerelease policy, and the release cutoff.

### Canonical highest resolution

The deterministic result chosen by the pinned `uv` version with `resolution=highest` for the recorded inputs. This is not described as the unique mathematical maximum: conflicting packages may admit multiple Pareto-optimal solutions.

### Validated candidate

A candidate that passed every required deterministic, integration, container, security, and live-canary gate against the recorded base commit. It remains subject to maintainer review.

## Source of Truth

`pyproject.toml` becomes the only manually edited dependency manifest:

- `[project.dependencies]` contains runtime dependencies;
- `[dependency-groups].dev` contains test and development dependencies;
- `[tool.uv] package = false` declares this repository as an application rather than a publishable package;
- `requires-python` is constrained to the supported Python 3.14 series.

`uv.lock` becomes the only committed exact dependency graph. It is generated by a pinned `uv` release and committed.

`requirements.txt` and `requirements-dev.txt` cease to be independent inputs. Any requirements-format file needed by `pip-audit` or another compatibility tool is exported temporarily from `uv.lock` and is never hand-maintained.

Repository-specific audit policy is explicit rather than embedded in workflow shell:

```toml
[tool.dependency-frontier]
python-version = "3.14"
production-platform = "x86_64-manylinux_2_28"
resolution-platforms = ["x86_64-manylinux_2_28", "x86_64-pc-windows-msvc"]
cooldown-days = 7
allowed-source-builds = []
license-denylist = []
```

An empty source-build allowlist means every candidate must provide a compatible wheel on the production platform. An empty license denylist makes license changes report-only until the repository adopts an explicit legal policy; the workflow must not invent one.

CI, local verification documentation, and Docker use locked installs. No production build may resolve unconstrained dependency ranges.

## Scheduled Discovery

### Cadence

- GitHub Actions wakes weekly on Monday at a non-peak minute.
- A fixed UTC epoch gate permits the full audit only every second Monday, producing an exact 14-day cadence across month and year boundaries.
- `workflow_dispatch` bypasses the cadence gate for manual runs.
- A failed scheduled run remains failed or inconclusive; it is never replaced by a successful “nothing to do” result. It may be rerun manually.

Dependabot uses its supported cron/natural schedule for the same two-week cadence. A seven-day update cooldown applies to normal version updates. Security updates do not wait for the cooldown.

### Frozen discovery window

At workflow start the audit computes an RFC 3339 cutoff exactly seven days before the recorded start time. All resolver invocations use that absolute cutoff. The report records:

- base commit SHA;
- cutoff timestamp;
- pinned `uv` version;
- Python version;
- target platform;
- hash of dependency inputs;
- prerelease and yanked-release policy.

Stable, non-yanked releases newer than the cutoff are deliberately excluded. This is reported as a safety cooldown, not presented as a lack of newer releases.

## Discovery Data Flow

1. Verify UTF-8 repository invariants and parse `pyproject.toml` with `tomllib` plus `packaging.Requirement`.
2. Reject malformed dependency metadata, duplicate canonical package names, unsupported direct URLs, or a missing Python constraint.
3. Verify `uv lock --check` and install the baseline into a clean environment with `uv sync --locked`.
4. Export and inspect the baseline graph.
5. Generate a policy input retaining all direct constraints.
6. Generate a frontier input removing only registry version specifiers. Preserve extras and markers exactly.
7. Compile both inputs separately for the declared Linux production and Windows development targets with the same absolute cutoff, Python 3.14, and `resolution=highest`; repeat every platform resolution and compare normalized results.
8. Parse exact direct and transitive versions from the generated requirements-format locks.
9. Classify each direct dependency as unchanged, update-within-policy, blocked-by-policy, major frontier update, or unresolved.
10. Preserve the complete candidate locks as workflow artifacts so validation jobs install the exact graphs that were reported.

The audit script must not edit `pyproject.toml`, `uv.lock`, or the default branch.

## Update Proposal Policy

Dependabot is responsible for ordinary dependency PR generation because it has native ecosystem knowledge and reduces custom mutation logic.

- Patch and minor production/dev updates are grouped into one PR.
- Major updates and updates that require widening a constraint are separate PRs.
- Transitive-only lock refreshes are included in the appropriate grouped PR.
- Automatic merge is disabled for every dependency PR.
- Open dependency PRs must rebase onto the latest base branch and rerun all required checks after another dependency PR merges.

The frontier audit independently checks for releases that Dependabot or current constraints do not propose. This redundancy prevents the bot from being the sole source of truth.

If two major upgrades fail independently but the combined frontier resolves and validates, the report marks them as a **coupled upgrade set**. No independent PR is called compatible. A coupled PR is created or prepared only with both changes and a clear explanation.

## Validation Gates

### Gate 0: Baseline health

- repository encoding check;
- `uv lock --check`;
- clean locked sync;
- dependency consistency check;
- baseline CI status for the exact base SHA.

If the baseline is unhealthy, candidate results are `blocked-baseline`. The system does not attribute existing failure to dependency updates.

### Gate 1: Resolution and integrity

- candidate lock is reproducible from its recorded inputs and cutoff;
- a second resolution produces the same normalized package/version/marker set;
- the candidate installs into a fresh environment;
- `uv pip check` reports no missing or conflicting packages;
- no unexpected registry, URL, editable, or local dependency source appears;
- all expected Linux wheels or explicitly allowed source builds exist for Python 3.14.

### Gate 2: Static and deterministic application checks

- Ruff lint and format;
- mypy for `app` and `bot.py`;
- encoding validation;
- full non-integration pytest suite;
- dependency boundary smoke tests.

Dependency boundary smoke tests exercise high-risk imported APIs rather than only importing modules:

- Telegram application/handler construction and polling signatures;
- Google GenAI client/request construction and response adaptation with deterministic transports;
- Quart application creation, routes, test client, and Hypercorn configuration;
- Pydantic settings validation;
- cryptography encrypt/decrypt round trip;
- pypdf, python-docx, and Pillow fixture processing;
- orjson/msgspec serialization;
- ephem/geonamescache natal readiness;
- Redis and asyncpg adapter construction.

### Gate 3: Service integration

Run serial integration tests against disposable services:

- PostgreSQL with pgvector and migrations applied repeatedly plus `--check`;
- Redis using a real ephemeral service rather than the local fallback;
- repository, queue, cache, metrics, and web integration tests;
- no production database or cache credentials.

### Gate 4: Production container

- build the production Dockerfile from the exact committed or candidate lock;
- verify the image uses the expected Python and dependency versions;
- run an offline container smoke command;
- start the web/health surface with disposable configuration and verify health/readiness;
- scan the installed graph with `pip-audit`;
- generate a CycloneDX SBOM and record added/removed packages;
- report license changes and fail only on an explicit denylist or unknown license policy, not on arbitrary heuristics.

### Gate 5: Controlled live canary

The live canary runs only after Gates 0–4 pass and after access to a protected `dependency-canary` GitHub Environment is approved. This prevents unreviewed package code from automatically receiving service credentials.

Credentials are dedicated, low-quota, revocable canary credentials. They must not access production databases, user chats, admin accounts, or production provider keys.

The live sequence uses the same minimal fixtures for baseline and candidate:

1. Telegram `getMe`, send one uniquely tagged message to a dedicated canary chat, then delete it.
2. Gemini sends one small deterministic prompt and validates a minimal response contract.
3. Tavily sends one low-cost query through the same `httpx` request contract used by the application and validates the normalized response contract.

Every call has a short timeout, request identifier, and at most one retry for errors already classified as transient. Cleanup runs in `finally` blocks. Failure to clean up is a failure.

### Baseline control for live services

The baseline and candidate are tested in the same canary window:

- baseline passes, candidate passes: live gate passes;
- baseline passes, candidate fails deterministically: candidate fails;
- baseline and candidate fail with a transient/provider signature: result is `inconclusive-external`;
- baseline authentication fails: result is `blocked-canary-configuration`;
- candidate authentication/API-shape failure while baseline passes: candidate fails;
- any missing secret or skipped required call: the live gate does not pass.

No `continue-on-error` or retry wrapper may convert an inconclusive or failed live gate into success.

## Status Model

Allowed terminal statuses are:

- `no-update` — no eligible change before the cutoff;
- `validated-candidate` — every required gate passed;
- `rejected-resolution` — no candidate graph exists or it is non-reproducible;
- `rejected-tests` — deterministic/integration/container test failed against a healthy baseline;
- `rejected-security` — known vulnerability, forbidden source, or explicit policy violation;
- `rejected-live` — baseline passed and the candidate failed a deterministic live contract;
- `blocked-baseline` — current base commit is unhealthy;
- `blocked-canary-configuration` — required protected credentials or configuration are invalid;
- `inconclusive-external` — provider/network control could not distinguish dependency failure from external instability;
- `cancelled` — workflow did not finish.

Only `validated-candidate` may be described as ready for maintainer review. No status triggers automatic merge.

## Reporting

Each run produces machine-readable JSON and human-readable Markdown with:

| Field | Meaning |
|---|---|
| Package | Canonical direct dependency name |
| Scope | production or development |
| Constraint | Committed direct requirement |
| Locked | Version used by the baseline on Linux/Python 3.14 |
| Policy | Highest version inside policy |
| Frontier | Canonical highest version with direct bounds removed |
| Change | patch, minor, major, pin/upper-bound blocked, or transitive-only |
| Resolution | resolver status and conflict explanation |
| Validation | highest completed gate and terminal status |

The report also includes transitive package changes, cutoff/tool/input metadata, vulnerabilities, SBOM delta, license delta, live request IDs without secrets, and links to logs/artifacts.

Scheduled runs write a GitHub job summary and upload artifacts. When actionable blocked/frontier updates exist without a PR, the workflow creates or updates one tracking issue instead of creating duplicate issues. Clean runs close the active tracking issue.

## Test Strategy for the Audit System

The audit implementation itself is test-driven. Unit and contract tests cover:

- PEP 508 names, extras, markers, comments, and canonicalization;
- removal of specifiers without altering markers/extras;
- exact pins, compatible releases, exclusions, and compound ranges;
- production/dev duplicate handling;
- prerelease, yanked, and cutoff behavior;
- direct versus transitive classification;
- semantic version classification including pre-1.0 releases;
- reproducibility comparison with normalized ordering;
- cadence calculation across month/year/ISO-week boundaries;
- baseline/candidate/live status transitions;
- missing secrets and provider error classification;
- coupled-major reporting;
- workflow contract assertions for lock use, permissions, no automerge, protected environment, and required checks.

Tests must use local fixtures and mocked subprocess/provider boundaries. Real live calls occur only in the protected canary workflow.

## Security Boundaries

- Resolution and deterministic testing jobs have read-only repository permissions and no service secrets.
- PRs from forks never receive canary secrets.
- The canary environment requires maintainer approval and exposes only dedicated canary credentials.
- Candidate lock sources and a first wheel-only installation are validated in an unprivileged job before any protected environment is entered. The protected job reproduces the same locked, no-source-build installation with checkout credentials disabled and injects dedicated service credentials only into the probe step.
- Logs redact tokens, URLs containing credentials, provider payload secrets, and database DSNs.
- Actions and the `uv` tool are version-pinned; dependency updates for CI tooling are reviewed separately.
- The seven-day cooldown is bypassed only for explicitly reviewed security fixes.

## Rollout

1. Migrate dependency declarations into `pyproject.toml` without changing the currently resolved production behavior.
2. Generate and verify the first real universal `uv.lock`.
3. Update local documentation, CI, and Docker to locked installs.
4. Add dependency frontier parsing/reporting with unit tests.
5. Add the scheduled workflow and Dependabot grouping without live credentials.
6. Add deterministic dependency boundary tests and Redis/container gates.
7. Add the protected live-canary script and tests.
8. Configure dedicated GitHub environment secrets and required checks outside the repository.
9. Run one manual frontier audit and review its report before relying on the two-week schedule.

## Non-Goals

- automatic merging or deployment of dependency updates;
- claiming proof of complete behavioral compatibility;
- testing against production user data or production credentials;
- automatically rewriting application code for major SDK migrations;
- accepting prerelease packages in the ordinary frontier;
- replacing maintainer review of changelogs, licenses, provenance, and breaking changes.

## Success Criteria

- A clean checkout installs the exact committed dependency graph locally, in CI, and in Docker.
- The audit reports versions hidden by current constraints and produces reproducible candidate locks.
- Patch/minor PRs are grouped; major PRs are isolated unless proven coupled.
- Every candidate is evaluated against a healthy baseline through all applicable gates.
- Missing secrets, external outages, cancellations, and skipped jobs cannot produce `validated-candidate`.
- The live canary uses only protected, dedicated, low-impact resources.
- No dependency PR can merge automatically.
