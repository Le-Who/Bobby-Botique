# Маршрутизация моделей для inline-раскладов Таро

## Контекст

Inline-обработчик Таро запускает `gemini-3.1-flash-lite` и
`gemini-3.5-flash` параллельно почти для всех раскладов, но ожидает успешный
ответ `gemini-3.5-flash` без ограничения по времени. Поэтому уже готовый
lite-ответ может удерживаться дольше общего inline-интервала ожидания.

## Требуемое поведение

Маршрутизация зависит только от выбранного inline-расклада:

| Расклад | Карты | Модели | Ожидание сильной модели |
| --- | ---: | --- | --- |
| `tarot_daily` | 1 | только `gemini-3.1-flash-lite` | нет |
| `tarot_yesno` | 1 | только `gemini-3.1-flash-lite` | нет |
| `tarot` | 3 | только `gemini-3.1-flash-lite` | нет |
| `tarot_love` | 5 | `gemini-3.5-flash` + горячий резерв `gemini-3.1-flash-lite` | не более 23 секунд |
| `tarot_celtic` | 6 | `gemini-3.5-flash` + горячий резерв `gemini-3.1-flash-lite` | не более 23 секунд |
| `tarot_fortune` | 0 | без LLM | нет |

Обычный неинлайновый сеанс Таро в `app/handlers/tarot_chat.py` не меняется.

## Поток генерации

Для `daily`, `yes/no` и классического трёхкарточного inline-расклада
обработчик делает один вызов через `ProviderRouter.get_response()` с моделью
`gemini-3.1-flash-lite` и существующим последовательным перебором ключей.

Для `relationship` и `celtic cross` обработчик одновременно запускает две
задачи через `ProviderRouter.get_response()`. Готовый lite-ответ удерживается,
пока сильная модель не вернёт пригодный ответ или пока не истекут 23 секунды с
момента запуска задач. При истечении лимита публикуется lite-ответ, а
незавершённая задача сильной модели отменяется и дожидается завершения отмены.

Если сильная модель раньше лимита возвращает исключение, пустой ответ или
маркированную ошибку провайдера, обработчик сразу переходит к lite-ответу. Если
lite-ответ непригоден, используется пригодный уже завершившийся ответ сильной
модели; иначе пользователю показывается существующее сообщение об ошибке с
кнопкой повтора. После выбора результата все незавершённые задачи отменяются.

## Структура кода

В `app/handlers/inline.py` появится отдельная константа 23-секундного лимита
для сложных раскладов и небольшая внутренняя функция, отвечающая только за
выбор модели, запуск задач и выбор пригодного результата. Формирование карт,
промпта и Telegram-сообщения останется в `_generate_tarot_inline()`.

Это сохраняет текущий `ProviderRouter`, ротацию ключей и обработку ошибок, не
смешивая непотоковый путь Таро с потоковым конвейером обычных inline-ответов.

## Проверка

Тесты должны доказать следующее:

1. `tarot_daily`, `tarot_yesno` и `tarot` вызывают только
   `gemini-3.1-flash-lite`.
2. `tarot_love` и `tarot_celtic` запускают обе модели.
3. При быстром пригодном ответе `gemini-3.5-flash` выбирается он.
4. При превышении настраиваемого в тесте лимита выбирается уже готовый
   lite-ответ, не ожидая завершения сильной модели.
5. Ранний сбой сильной модели немедленно переключает обработчик на lite.
6. Ошибки обеих моделей сохраняют существующий пользовательский fallback.
7. Существующие тесты обычного чат-сеанса Таро продолжают проходить без
   изменений.

## Вне области изменений

- Общий 13-секундный лимит обычных inline-ответов.
- Модели и логика обычного чат-сеанса Таро.
- Состав раскладов, выбор карт, тексты промптов и оформление ответа.
- Настройки квот, ключей и повторных попыток внутри `ProviderRouter`.
