# Управление каталогом моделей без статического allowlist

## Контекст и подтверждённые причины

`GEMINI_AVAILABLE_MODELS` проходит через статический
`CURRENT_GEMINI_MODELS`. Поэтому новая chat-capable модель, которой ещё нет в
исходном коде, удаляется из env-списка при загрузке. Та же проверка запрещает
добавить модель через `/models`.

Кроме того, `sync_models_from_db()` сохраняет первоначальный env-список в
`global_settings`, а на следующих стартах считает эту копию явным override.
После изменения GitHub Secret старое значение из БД безусловно побеждает новый
env. Кнопка «Сбросить к .env» обходит этот эффект, потому что вручную читает env
и перезаписывает строку БД.

Наконец, `add_model()` возвращает один `False` для пустого имени, дубликата и
неподдерживаемой Gemini-модели. Обработчик интерпретирует любой `False` как
дубликат, из-за чего пользователь получает ложное сообщение «уже есть».

В текущем исходном коде уже создаются кнопки удаления, но этот путь не покрыт
тестами. Полное имя модели в `callback_data` также может превысить
64-байтный лимит Telegram для длинных идентификаторов провайдеров.

## Цели

1. Новый корректный Gemini model ID должен работать без выпуска новой версии
   бота и без добавления в статический allowlist.
2. Изменение `*_AVAILABLE_MODELS` должно применяться после рестарта, если
   администратор не создал явный runtime override.
3. Явные изменения через `/models` должны сохраняться между рестартами и иметь
   понятный приоритет над env до команды сброса.
4. Добавление должно различать успех, дубликат, некорректное имя,
   неподдерживаемую модель и временную невозможность проверки.
5. `/models` должен позволять безопасно удалять модели всех поддерживаемых
   chat-провайдеров.
6. Должен существовать однозначный способ намеренно оставить провайдера без
   пользовательских вариантов, не ломая его внутренние служебные вызовы.

## Источники конфигурации и приоритет

Для каждого провайдера существует env baseline и необязательный admin override:

1. Если в БД есть запись схемы v2 с `source: "admin"`, активен точный список из
   неё.
2. Иначе активен актуальный env baseline.
3. «Сбросить к .env» удаляет запись override, а не сохраняет копию env в БД.
4. Сам env baseline никогда автоматически не записывается в БД.

Запись override использует JSON-объект, а не неразмеченный JSON-массив:

```json
{
  "version": 2,
  "source": "admin",
  "models": ["gemini-3.7-flash", "gemini-3.5-flash-lite"]
}
```

Старый JSON-массив не позволяет отличить автоматически сохранённый baseline
от ручного изменения. При первом запуске новой версии такая legacy-запись
считается старым baseline, удаляется и заменяется текущим env в памяти. Это
одноразовая миграция, необходимая для устранения существующей рассинхронизации.
В лог записываются провайдер и факт миграции, но не API-ключи.

Экран `/models` явно показывает `Источник: env` или
`Источник: /models override`. Поэтому ожидаемое поведение после изменения
Secret не зависит от скрытого состояния БД.

## Парсинг пустого списка

Для `GEMINI_AVAILABLE_MODELS`, `OPENCODE_AVAILABLE_MODELS`,
`OPENROUTER_AVAILABLE_MODELS` и `FREETHEAI_AVAILABLE_MODELS` вводится единый
контракт:

- переменная не задана или после trim пуста — используются существующие
  provider-specific defaults;
- значение `none` без учёта регистра и окружающих пробелов — пользовательский
  список намеренно пуст;
- любое другое значение — точный comma-separated список с trim, удалением
  пустых элементов и стабильной дедупликацией.

Один пробел не является командой очистки: в GitHub Actions отсутствующий Secret
и пустое значение трудно надёжно различить. Для очистки документируется только
явный sentinel `none`.

`AVAILABLE_MODELS` означает именно модели, доступные пользователю в `/model`.
`DEFAULT_MODEL`, `QNA_MODEL`, `RESEARCH_MODEL` и другие role-модели больше не
добавляются в этот список автоматически. Они остаются отдельной runtime-
конфигурацией и могут использоваться внутренними сценариями, даже если модель
скрыта из selector.

Если пользовательские списки всех провайдеров пусты, `/model` показывает
понятное сообщение без кнопок моделей. Reload не выполняет массовую миграцию
существующих чатов при отсутствии безопасной selectable-модели назначения.

## Gemini model IDs и capability validation

`CURRENT_GEMINI_MODELS` перестаёт быть критерием допустимости. Из него и других
hardcoded-констант формируется только известный порядок fallback.

Env считается доверенной операторской конфигурацией: при синхронной загрузке
проверяются только trim, отсутствие пробелов/управляющих символов и префикс
`gemini-`. Это позволяет новой модели появиться немедленно и не создаёт сетевую
зависимость при старте.

Добавление Gemini-модели из Telegram является недоверенным runtime-вводом и
проверяется через Gemini Models API. Модель принимается, если `models.get`
возвращает её и в `supportedGenerationMethods` присутствует
`generateContent`. Проверка перебирает настроенные Gemini-ключи до
определённого ответа:

- модель существует и поддерживает `generateContent` — добавить;
- получен определённый `not found` или capability отсутствует —
  `unsupported`;
- все попытки завершились transport/auth/rate-limit ошибками —
  `validation_unavailable`, список не менять.

Тесты используют внедрённый validator и не обращаются в сеть.

Новая сквозная проверка должна убрать использование
`CURRENT_GEMINI_MODELS` как eligibility-фильтра из config loader,
`models_repo`, fallback router и agent use cases. Произвольная настроенная
Gemini chat-модель остаётся прямой целью вызова; известные константы
используются только как последующие fallback-кандидаты.

## Repository API

Provider metadata хранится в едином registry: provider ID, settings attribute,
env variable, display label, default baseline и необязательный validator.
Неизвестный provider отклоняется явно и больше не попадает по умолчанию в
`OPENCODE_AVAILABLE_MODELS`.

`get_model_catalog(provider)` возвращает immutable-снимок:

- `provider`;
- `models`;
- `source` (`env` или `admin` ).

`add_model()` и `remove_model()` возвращают типизированный результат с кодом:

- `added`;
- `removed`;
- `duplicate`;
- `not_found`;
- `invalid`;
- `unsupported`;
- `validation_unavailable`;
- `unknown_provider`.

Успешная мутация записывает полный точный v2 override и атомарно обновляет
live settings. Неуспешная мутация не меняет ни БД, ни память.

## `/models` UX

Provider selector включает Gemini, Opencode Go, OpenRouter и FreeTheAI.
Экран провайдера показывает источник и текущий список. Для каждой модели
создаётся явная кнопка `❌ <model>`.

В callback передаётся provider и короткий стабильный token, рассчитанный из
имени модели; полное имя в callback не помещается. При обработке token повторно
разрешается по текущему snapshot. Если список успел измениться, бот сообщает об
устаревшем экране и предлагает открыть его заново.

После успешного удаления экран списка сразу перерисовывается с коротким
подтверждением. Удаление последней модели разрешено и создаёт пустой admin
override. «Сбросить к .env» удаляет override и восстанавливает baseline.

Сообщение добавления выбирается по точному result code. В частности,
`unsupported` и `validation_unavailable` никогда не отображаются как
«уже есть».

## Reload и миграция пользовательских чатов

`get_all_available_models()` возвращает только объединение selectable-
списков. После reload пользователи с удалённой моделью мигрируются только на
модель, которая действительно присутствует в новом объединении.

Если у удалённого провайдера есть selectable default, используется он. Иначе
используется первый доступный вариант другого провайдера. Если объединение
пусто, миграция пропускается и существующие чаты остаются неизменными.

Внутренние маршруты Q&A, research, inline, grounding и fallback продолжают
использовать role-модели независимо от видимости в `/model`.

## Обработка ошибок и наблюдаемость

- Ошибочный env model ID не исправляется молча и не заменяется другой моделью;
  loader выдаёт предупреждение с именем переменной и элемента.
- Невалидная или неизвестная DB-схема не применяется; бот использует env и
  пишет диагностическое предупреждение.
- Ошибка записи override не должна оставлять live settings в состоянии,
  отличном от БД: сначала выполняется успешная запись, затем меняется память.
- Логи синхронизации содержат provider, source и число моделей, но не секреты.
- Ошибка remote capability validation показывает администратору отдельное
  retry-сообщение.

## TDD и проверка

До production-кода добавляются регрессионные тесты, которые сначала должны
упасть по ожидаемой причине:

1. `GEMINI_AVAILABLE_MODELS` сохраняет точный порядок списка с
   `gemini-3.7-flash` и не добавляет hardcoded-модели.
2. Unset/blank и `none` различаются для каждого provider-specific baseline.
3. Legacy DB-массив игнорируется и удаляется; v2 admin override побеждает env;
   reset удаляет override и возвращает актуальный env.
4. Изменённый env применяется после рестарта при отсутствии admin override.
5. Результаты add/remove различают все пользовательские исходы и не изменяют
   состояние при ошибке.
6. Gemini validator принимает `generateContent`, отклоняет non-chat/404 и
   отдельно сообщает временную невозможность проверки.
7. `/models` показывает source, все четыре провайдера, рабочие delete-кнопки с
   callback короче 64 байт и обновлённый список после удаления.
8. `/model` корректно отображает отдельные пустые provider-списки и полностью
   пустой каталог.
9. Reload не мигрирует пользователей при полностью пустом каталоге и никогда
   не выбирает скрытую default-модель.
10. Новая Gemini-модель проходит прямую маршрутизацию, а статический список
    остаётся только fallback-порядком.
11. Существующие целевые и полные тесты проходят; до и после документационных
    изменений проходит `scripts/check_encoding.py`.

## Документация и область изменений

README и CHANGELOG описывают:

- точную семантику env/admin precedence;
- sentinel `none` и предупреждение не использовать пробел;
- dynamic Gemini validation;
- удаление и reset через `/models`;
- поддержку всех четырёх chat-провайдеров.

GitHub Actions workflow уже передаёт все четыре `*_AVAILABLE_MODELS` в SSH-
окружение и Docker-контейнер, поэтому изменение механики доставки Secret не
требуется.

Вне области изменений: получение и ротация API-ключей, модельные квоты,
выбор image/audio/live-моделей, формат пользовательских ответов и логика
провайдеров, не связанная с выбором или fallback chat-моделей.
