# Устойчивость Daily Trivia и восстановление административной наблюдаемости

Дата: 2026-08-29
Статус: согласовано пользователем, готово к реализации через TDD

## Контекст

Инцидент затрагивает пять связанных областей: генерацию Daily Trivia, первичное сохранение настроек подписки на гороскоп, возврат в `/help`, полноту `/admin` и основную административную панель. Проверка приложенного лога, скриншотов, обработчиков, репозиториев, роутера провайдеров, шаблона Dashboard и существующих тестов показала, что это не один сбой интерфейса, а несколько независимых первопричин.

Эта спецификация расширяет документ [2026-08-17-daily-trivia-model-routing-design.md](./2026-08-17-daily-trivia-model-routing-design.md). Его решения о поддержке алиасов и прямых Gemini model ID, едином значении модели для ручной и автоматической генерации и ранней обработке тегированных ошибок провайдера сохраняются. Ранее исключённые из объёма вопросы учёта неуспешных запросов в RPD и порядка смены ключей теперь входят в объём этой работы.

## Подтверждённые первопричины

### Daily Trivia

- Внешний цикл `generate_question_lane` трижды вызывает роутер с одной и той же preferred model. Он не задаёт требуемую последовательность `gemini-3.7-flash → gemini-3.6-flash → gemini-3.7-flash → gemini-3.6-flash`.
- Внутри роутера при временной ошибке сначала перебираются и приостанавливаются ключи, и только после исчерпания ключей рассматривается fallback модели. Поэтому один сбой модели способен преждевременно «сжечь» пул ключей, не проверив альтернативную модель на том же ключе.
- Счётчик `key_usage` увеличивается только после успешного ответа. Неуспешный запрос также расходует RPD провайдера, но сейчас остаётся невидимым планировщику и может привести к превышению дневного лимита.
- Предварительная генерация дат выполняется последовательно и завершается на первой ошибке. Почасовой запуск планировщика не различает срочную генерацию на сегодня и несрочный запас на будущие дни.

### Подписка на гороскоп

`upsert_horoscope_subscription` передаёт выбранные времена в ветку `DO UPDATE`, но начальный `INSERT` создаёт только `user_id` и `sign`. У новой записи оба времени остаются `NULL`, после чего `/horoscope_settings` корректно отображает фактические значения как «отключено». Ошибка находится в сохранении, а не в форматировании сообщения.

### `/help`

Полный каталог помощи уже централизован, однако команда и callback-навигация формируют представление и клавиатуры разными путями. Язык повторно определяется при переходах, а callback не несёт выбранный язык. В результате возврат может открыть другое представление или язык. Существующие тесты проверяют каталог, но не цикл «справка → раздел → назад».

### `/admin`

Текст `/admin` поддерживается вручную и не является полным отражением зарегистрированных административных команд. В частности, в нём отсутствуют команды обложек, а Dashboard и Daily Admin не представлены как явные точки входа. Тест проверяет только наличие слова `Admin`, поэтому расхождение не обнаруживается.

### Admin Dashboard

- Фронтенд игнорирует существующий пакетный `/api/dashboard` и каждые 15 секунд делает серию запросов к устаревшим endpoint-ам.
- Названия полей не согласованы: интерфейс ждёт `request_count` и `error_count`, а метрики возвращают `total_requests` и не отдают канонический `error_count`.
- Cache card обращается к несуществующим полям (`hits`, `misses`, `redis_hits`, `total_items`) и поэтому показывает прочерки.
- `/api/key-health` возвращает summary-объект с массивом в `keys`, а фронтенд воспринимает верхний объект как массив строк ключей; это приводит к ошибке рендера.
- Запрос статистики Gemini скрывает ключи и модели с нулевым использованием из-за фильтра по присоединённой таблице usage.
- Ошибки загружаются из БД от новых к старым, добавляются в deque в том же порядке, а затем берётся хвост. Пользователь получает самые старые записи из загруженного окна вместо последних.

## Цели

1. Сделать генерацию Trivia предсказуемой на уровне пары «ключ + модель»: чередовать две выбранные модели до смены ключа.
2. Учитывать каждый фактически отправленный Gemini-запрос в RPD независимо от результата.
3. Не перегружать провайдера повторной предварительной генерацией: будущие даты повторять раз в несколько часов, срочную дату «сегодня» продолжать проверять ежечасно.
4. Сохранять времена новой подписки на гороскоп при первом `INSERT`.
5. Гарантировать актуальную и языково стабильную навигацию `/help`.
6. Сделать `/admin` полным отражением реально доступных административных команд и добавить прямые входы в обе панели.
7. Восстановить Overview, AI Providers, Infrastructure и Errors на одном каноническом snapshot API.

## Не входит в объём

- Изменение продуктовой логики самих вопросов Trivia, промпта или проверки ответа игрока.
- Изменение лимитов Gemini, тарифов либо времени суточного сброса RPD.
- Полный редизайн визуального стиля Dashboard или Daily Admin.
- Изменение состава публичных команд бота, кроме представления и навигации справки.
- Миграция существующих пользователей гороскопа с намеренно отключёнными временами: исправляется создание новых подписок и последующие явные изменения.

## Выбранный подход

Принят локализованный сценарий генерации Trivia. Он не меняет глобальный порядок fallback для чата, inline-режима и других AI-функций, где увеличение задержки может ухудшить пользовательский опыт. Для фоновой генерации будет выделен точный retry-plan, выполняемый роутером с закреплённым ключом.

Рассматривались также два варианта:

1. Глобально поменять роутер на «модели раньше ключей». Это проще концептуально, но изменяет задержки и семантику всех потребителей.
2. Оставить роутер без изменений и четыре раза вызывать его с разными preferred model. Такой вариант не удерживает один ключ на протяжении цикла и поэтому не обеспечивает требуемый момент ротации.

Выбранный вариант добавляет небольшой общий примитив выполнения явно заданного плана, но активирует новую политику только для Trivia.

## Проектирование изменений

### 1. Закреплённый retry-plan Daily Trivia

Для одной логической попытки генерации формируется цикл:

1. текущий ключ + `gemini-3.7-flash`;
2. тот же ключ + `gemini-3.6-flash`;
3. тот же ключ + `gemini-3.7-flash`;
4. тот же ключ + `gemini-3.6-flash`;
5. при отсутствии успешного результата перейти к следующему доступному ключу и повторить цикл.

Первая позиция в паре означает настроенную primary model для Trivia, а вторая фиксирована как известный runtime-кандидат `gemini-3.6-flash`; отдельная новая настройка для неё не вводится. Если в конфигурации задан прямой model ID или поддерживаемый алиас, резолвер сначала получает конкретный primary ID. При текущей настройке получается точная согласованная последовательность `gemini-3.7-flash → gemini-3.6-flash → gemini-3.7-flash → gemini-3.6-flash`. Если primary уже равна `gemini-3.6-flash`, дубликаты не удаляются автоматически: позиции остаются отдельными фактическими попытками, поскольку пользователь запросил повтор модели.

Роутер получает новый метод для выполнения явного плана с такими свойствами:

- ключ выбирается один раз на полный четырёхшаговый цикл;
- автоматический внутренний fallback моделей для отдельного шага отключён;
- автоматическая ротация ключа внутри шага отключена;
- ответ возвращает диагностическую информацию о фактических попытках без раскрытия ключа;
- после полного провала ключ приостанавливается только если классификация ошибки действительно относится к ключу или квоте;
- временная ошибка конкретной модели не делает ключ непригодным для следующей модели;
- невалидный ключ, authentication/permission error или исчерпанный дневной лимит немедленно завершает цикл этого ключа и переводит выполнение к следующему ключу;
- форматные ошибки ответа и ошибки JSON считаются ошибкой попытки генерации, но не ошибкой ключа.

Существующее число внешних попыток в `generate_question_lane` заменяется одним явным plan execution, чтобы не получить скрытое умножение `3 × 4 × количество ключей`. Парсинг и проверка содержимого выполняются после каждого успешного транспорта. Если транспорт успешен, но ответ невалиден, следующий шаг плана используется как следующая попытка.

### 2. Точный учёт RPD

Инкремент usage выполняется непосредственно вокруг фактического сетевого вызова, а не после успешного ответа:

- счётчик увеличивается ровно один раз, когда запрос был отправлен провайдеру;
- успешный ответ не вызывает второй инкремент;
- timeout после отправки, 4xx/5xx и provider-tag error учитываются;
- ошибка до отправки запроса, например отсутствие ключа или локальная валидация конфигурации, не учитывается;
- каждый шаг четырёхшагового плана считается отдельно по фактически использованным key/model;
- проверка доступности следующей попытки снова читает обновлённый usage, поэтому достигший порога ключ больше не выбирается для этой модели.

Для защиты от гонок репозиторий usage должен предоставить атомарную операцию «зарезервировать один RPD, только если лимит ещё не достигнут». Она возвращает признак успеха и новое значение. Сетевой вызов разрешён только после успешного резервирования. Это предотвращает одновременный выход нескольких воркеров за лимит. Существующая дата сброса и раздельный учёт по key/model сохраняются.

Если запрос не удалось физически отправить после успешного резервирования из-за локального исключения создания клиента, резерв не откатывается: консервативный перерасход на единицу безопаснее недоучёта. Такие случаи логируются отдельной причиной.

### 3. Повтор предварительной генерации

После провала подготовки будущей даты ставится cooldown на 3 часа. Ключ cooldown включает тип игры и дату пазла. Хранилище — Redis TTL; при недоступном Redis используется in-memory TTL текущего процесса.

- Дата «сегодня» не получает трёхчасовую паузу и повторяется при каждом штатном почасовом запуске, чтобы не пропустить доставку.
- Будущая дата в cooldown пропускается, но цикл продолжает обработку остальных дат; одна ошибка больше не обрывает весь запас.
- Успешная подготовка удаляет cooldown.
- Ручная административная генерация обходит cooldown, но использует тот же retry-plan и RPD-ограничения.
- В логах фиксируются дата, причина, время следующей допустимой попытки, число фактических запросов и обезличенный идентификатор ключа.

Отдельный новый cron не нужен: существующий почасовой job остаётся источником запуска и сам решает, какие даты уже можно повторить.

### 4. Первичная запись гороскопа

`upsert_horoscope_subscription` строит динамический `INSERT` из всех реально переданных полей, включая `time_today`, `time_tomorrow`, `timezone_offset` и `is_active`. `ON CONFLICT DO UPDATE` продолжает изменять только явно переданные поля.

Семантика `_MISSING` сохраняется:

- `_MISSING` означает «не менять существующее поле и не включать его в первичный INSERT»;
- явный `None` означает «сохранить NULL/отключить время»;
- конкретное значение времени должно попасть и в новый INSERT, и в конфликтное обновление.

Схема БД не меняется.

### 5. Единое представление `/help`

Команда и callback используют один renderer текста и один builder клавиатуры поверх централизованного каталога команд. Начальный язык выбирается один раз текущим языковым резолвером, сохраняется в `context.user_data` и кодируется в новых callback data:

- `help:<lang>` — обзор;
- `help_topic:<lang>:<slug>` — раздел.

Callback больше не переопределяет язык из `Telegram language_code`. Для старых кнопок `help` и `help_topic:<slug>` остаётся совместимый обработчик: он использует сохранённый язык, а при его отсутствии — штатный резолвер.

Обзор, открытый командой, и обзор после кнопки «назад» должны быть текстово идентичны и содержать полный актуальный каталог на выбранном языке. Клавиатура команды также содержит явный возврат в главное меню. Английский каталог остаётся полноценным; пользователь с английским Telegram не должен попадать в старую сокращённую версию.

### 6. Каталог `/admin`

Вводится `ADMIN_COMMAND_GROUPS` — структурированный источник правды для текста и клавиатуры `/admin`. Каждая запись содержит command, краткое описание и группу. Renderer не дублирует команды вручную.

Тест сопоставляет каталог с реально зарегистрированными административными обработчиками. Команды могут отсутствовать в справке только через явный `ADMIN_HELP_HIDDEN_COMMANDS` с причиной. Это позволяет осознанно скрывать, например, внутренний `/asr`, но не терять новые команды случайно.

Меню включает существующие команды обложек и две URL/WebApp-кнопки:

- `Dashboard` → корень административного приложения;
- `Daily Admin` → `/admin_daily`.

Кнопки показываются только при корректно настроенном публичном base URL. При его отсутствии текстовая справка остаётся полностью работоспособной.

### 7. Канонический snapshot Dashboard

Backend формирует один нормализованный snapshot и отдаёт его через аутентифицированный `/api/dashboard`. Frontend выполняет один запрос при загрузке и одном интервале refresh. SSE может инициировать более ранний refresh, но не создаёт отдельные несовместимые модели данных.

Каноническая структура:

```text
overview
  system, services
  metrics
  summarization
providers
  gemini, tavily, circuit_breakers, key_health
infrastructure
  database, queue, cache
errors
  count, rate_percent, recent
generated_at
```

Обязательные поля метрик имеют однозначные имена и единицы:

- `total_requests`;
- `average_response_time_ms`;
- `error_count`;
- `error_rate_percent`;
- `cache_hit_rate_percent`.

Cache DTO явно нормализует доступные значения для Redis и memory: status, item count, capacity/utilization и доступные hit/miss counters. Неизвестное значение передаётся как `null`, а не как выдуманный ноль. Карточка показывает `Unavailable`, если источник недоступен, и `—` только для конкретно отсутствующего поля.

Gemini usage строится как полный набор «настроенная модель × настроенный ключ» с LEFT JOIN usage/status, поэтому нулевое использование отображается как `0`, а не исчезает. Key Health использует колонки `Key`, `Model`, `Status`, `Failures`, `Suspended Until`, `Last Error`, соответствующие backend DTO.

Errors DTO возвращает фактический count, процент и последние записи в порядке newest-first. Загрузка deque из БД нормализует порядок до добавления, чтобы хвост всегда означал самые новые события. Текст ошибок экранируется перед вставкой в HTML.

Старые endpoint-ы сохраняются как совместимые wrappers над теми же нормализаторами, если их используют внешние потребители. Они не должны иметь отдельную бизнес-логику. README после реализации должен соответствовать фактическому одному RTT.

## Обработка ошибок и наблюдаемость

Ошибки Gemini классифицируются минимум как authentication, quota/RPD, transient transport/provider, content/parse и local preflight. Только первые две категории немедленно меняют ключ; transient продолжает заданную модельную последовательность на том же ключе; content/parse не приостанавливает ключ.

Секреты не попадают в логи или API. Для корреляции используется существующая маска либо необратимый короткий fingerprint. Snapshot Dashboard не возвращает полный API key.

Частичный отказ одного источника статистики не роняет весь `/api/dashboard`: соответствующая секция получает `available: false`, безопасное сообщение и `null` в недоступных полях. HTTP 500 используется только если невозможно сформировать сам envelope или пройти аутентификацию по штатным правилам.

## Стратегия тестирования (TDD)

Перед каждым изменением реализации добавляется тест, который падает по ожидаемой причине.

### Trivia и RPD

- unit: фактический порядок вызовов для одного ключа равен `3.7, 3.6, 3.7, 3.6`;
- unit: второй ключ выбирается только после полного цикла первого;
- unit: auth/quota error немедленно переключает ключ;
- unit: transient и parse error не приостанавливают ключ преждевременно;
- unit: каждый отправленный успешный, ошибочный и timeout-запрос увеличивает usage ровно один раз;
- unit: локальная ошибка до отправки не увеличивает usage;
- repository/concurrency: атомарное резервирование не допускает значение выше лимита;
- scheduler: будущая дата после ошибки пропускается 3 часа, сегодняшняя повторяется в следующий час;
- scheduler: ошибка одной будущей даты не мешает обработке следующих дат;
- scheduler: ручной запуск обходит cooldown.

### Гороскоп

- repository unit: первый INSERT содержит все переданные времена, timezone и active;
- repository unit: `_MISSING` не перезаписывает поле, а явный `None` записывает NULL;
- integration при доступной БД: новая подписка затем читается с выбранными временами;
- handler: подтверждение подписки и `/horoscope_settings` показывают одинаковые значения.

### Help и Admin

- RU и EN: `help → topic → back` возвращает идентичный полный обзор;
- callback не меняет язык при Telegram locale, отличном от выбранного языка;
- legacy callback data остаётся работоспособной;
- команда и callback используют одинаковую клавиатуру разделов и возврат в главное меню;
- admin catalog покрывает зарегистрированные admin-команды за вычетом явного hidden set;
- `/admin` содержит команды обложек;
- dashboard-кнопки формируются только для валидного base URL.

### Dashboard

- snapshot contract: все четыре секции и канонические поля присутствуют;
- frontend contract/DOM: один refresh создаёт один `/api/dashboard` request;
- метрики показывают `total_requests` и реальный `error_count`;
- cache DTO и карточка согласованы;
- key-health rows рендерятся из вложенного массива, без TypeError;
- Gemini rows включают неиспользованные модели/ключи;
- ошибки отсортированы newest-first;
- частичный отказ зависимости помечает только свою секцию unavailable;
- строки ошибок экранируются;
- legacy endpoint-ы возвращают данные тех же нормализаторов.

После точечных тестов выполняются все затронутые наборы, затем полный `pytest`. Для документации до и после записи запускается `python scripts/check_encoding.py`.

## Совместимость и данные

- Миграция схемы не требуется: RPD продолжает использовать `key_usage`, cooldown — Redis/in-memory TTL, подписка — существующие столбцы.
- Изменение атомарности usage реализуется совместимо с текущими строками и суточным ключом даты.
- Старые help callback data и legacy Dashboard API остаются доступными.
- Конфигурация прямых Gemini model ID и алиасов из предыдущей Trivia-спецификации сохраняется.

## Порядок реализации

1. Зафиксировать красными тестами RPD reservation и закреплённый retry-plan.
2. Реализовать repository primitive и локальный Trivia executor, затем cooldown планировщика.
3. Добавить красные тесты и исправить первичный horoscope INSERT.
4. Объединить help renderer/navigation и построить admin catalog с тестами покрытия.
5. Ввести snapshot DTO/service, переключить Dashboard на один endpoint и исправить порядок ошибок/нулевые Gemini rows.
6. Запустить точечные и полные тесты, encoding check, проверить Dashboard в браузере при доступной локальной среде.

## Критерии приёмки

- Лог генерации одного полностью неуспешного ключа показывает ровно четыре модельных шага в согласованном порядке до смены ключа.
- RPD usage не ниже количества реально отправленных запросов, включая ошибки; допускается только консервативно зарезервированный слот для неоднозначного локального сбоя непосредственно при отправке.
- Ошибочная будущая заготовка повторяется не чаще чем раз в 3 часа, а сегодняшняя не блокируется cooldown.
- Новая подписка сразу показывает выбранные времена в `/horoscope_settings`.
- Возврат из любого раздела `/help` сохраняет язык и полный актуальный текст.
- `/admin` покрывает зарегистрированные команды согласно явной политике скрытия и даёт доступ к обеим панелям.
- Overview, AI Providers, Infrastructure и Errors заполняются через один `/api/dashboard`; частичный отказ отображается локально и не ломает остальные вкладки.
- Все затронутые и полные тесты проходят, UTF-8 проверка успешна.
