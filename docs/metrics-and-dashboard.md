# Метрики и мониторинг

Текущий контракт учёта и главной панели `/`. Настройки процессов, промптов и
моделей описаны отдельно в [runtime controls](runtime-controls.md), а приватный
журнал событий — в [logging runbook](logging.md).

## Обращения пользователей и вызовы API

В блоке **Workload** показаны два разных счётчика:

- **User requests** — завершённые принятые операции помощника. Владелец входного
  запроса записывает одну операцию после обработки текста, фото, голосового
  сообщения, inline-запроса или выполнения действия из кнопки. Прямая озвучка
  учитывается после постановки в голосовую очередь; уточнение источника тоже
  считается обработанным обращением. Внутренние этапы, резервные модели и повторы
  не добавляют пользовательских обращений. Отказы до принятия, навигация по меню
  и отменённые операции в этот счётчик не входят.
- **API attempts** — зарегистрированные отправки запросов к внешним сервисам:
  моделям, синтезу и распознаванию речи, embeddings, поиску и вспомогательным
  API. Неудачная или отменённая отправленная попытка учитывается; локальный отказ
  по квоте до отправки — нет. Гонки моделей и ключей, повторы и фоновые операции
  могут создавать несколько попыток на одно пользовательское обращение.

Например, одна длинная просьба озвучить текст, которую Telegram разделил на
несколько исходных сообщений, учитывается как одна принятая пользовательская
операция сборки. Полные источники получают отдельные задания; проверенный
короткий хвост может войти в предыдущее. Необходимые внутренние TTS-части и повтор после явного обрезания
дают отдельные API attempts и резервирования квот. Они выполняются
последовательно, без гонки копий одного текста. Новых текстовых генераций для
прямой озвучки нет. Правила сборки и её границы — в
[руководстве по длинной озвучке](voice-and-tts.md#длинный-текст-из-нескольких-telegram-сообщений).

Вызов Gemini `countTokens` также является отдельной API attempt с workload
`tts.token_count`, но не генерирует текст/аудио и не списывает локальную квоту
TTS-генераций RPM/RPD. Обычный помещающийся источник требует одного подсчёта
и одного синтеза. Повторное использование проверенного результата в очереди
или на другом ключе не создаёт нового подсчёта; смена модели/содержимого/метаданных
требует своей проверки. Поэтому API attempts и расход генераций ключа могут
отличаться без двойного списания.

Это прикладная телеметрия инструментированных вызовов, а не биллинг провайдера,
счётчик всех HTTP-пакетов или всех Telegram updates. Доставка сообщений Telegram,
загрузка локального интерфейса и его обновления не являются попытками генерации.
Число ключей не задаёт верхнюю границу всех попыток: неудачи, другие сервисы и
фоновые задачи также расходуют вызовы.

Время в селекторе задаёт календарные периоды **Europe/Kyiv**:

| Период | Начало | Конец |
| --- | --- | --- |
| Today | Полночь текущего дня | Время снимка |
| Last 7 calendar days | Полночь шесть дней назад | Время снимка |
| Last 30 calendar days | Полночь 29 дней назад | Время снимка |

Это не скользящие интервалы по 24 часа. Панель показывает обе границы; переход
на летнее или зимнее время учитывается часовым поясом. SSE обновляет эти же
календарные значения и сохраняет выбранный период.

Исторические пользовательские итоги берутся из `user_metrics`, к которым
добавляются ещё не сохранённые события текущего процесса. Старое поле
`metrics.request_count` смешивало внутренние и пользовательские этапы и не служит
источником нового счётчика. Старые `api_calls` содержали логические этапы и
синтетические операции; преобразовывать их в точное число отправок нельзя.

Новый учёт API хранится отдельно в `traffic_daily`. `traffic_accounting_epoch`
сохраняет время первого включения инструментирования. Если выбранный период
начинается раньше, панель показывает **Partial API coverage** и дату начала
измерений. Прежние неизвестные вызовы не подменяются нулём или старым смешанным
итогом. При недоступной БД/неактивированном учёте показано **Unavailable**.
Полное временное покрытие означает работу текущего инструментирования в течение
периода, а не сверку с провайдерским биллингом.

## Сохранение и восстановление

Очередь событий обрабатывается в фоне; запись выполняется примерно раз в пять
минут и при штатном завершении процесса. Сохранённые дневные итоги загружаются
для чтения и не возвращаются в очередь новых дельт. Снимок панели синхронизирован
с записью: он не складывает уже сохранённую дельту с той же дельтой в памяти и
не теряет её на время записи. Событие закрепляет день при поступлении; отложенная
запись после полуночи сохраняет исходный день.

Для API у каждой пары «день, экземпляр процесса» хранится накопленный максимум.
Повторная запись того же значения, в том числе после потери подтверждения БД,
не прибавляет его ещё раз. Новый процесс получает отдельный идентификатор.
При временной ошибке активации эпохи обработчик событий продолжает работать,
а запись эпохи повторяется при следующем сохранении. Нештатное завершение до
сохранения может потерять события в памяти; эти данные не являются аудитом
финансовых операций.

Исправление загрузки старых дельт само по себе не исправляет уже завышенные
строки. Для восстановления нужны ограниченная резервная копия агрегатов,
сверка с пользовательскими итогами/терминальными событиями, предварительный
расчёт и транзакция с проверкой исходных значений. При новых данных операция
должна остановиться для пересчёта. Повторное применение принятого исправления
не должно менять результат. Реальные `key_usage` и резервирования квот не
исправляются по ошибочному общему счётчику. Приватные журналы и резервные копии
не включаются в репозиторий.

## Модели и ключи

В **Gemini key usage** каждая модель показана одной свёрнутой группой. Заголовок
содержит точный model ID, число ключей, суммарный локальный расход и состояние
локального допуска. Различные model ID не объединяются по похожему имени.
Раскрытие показывает расход, предел и допуск каждого маскированного ключа.

Поиск работает по model ID и маскированной части ключа. Доступна сортировка по
имени, расходу и близости к локальному порогу допуска, а также раскрытие и
сворачивание всех видимых групп. Обновления сохраняют поиск, сортировку и
раскрытые модели; новые группы появляются свёрнутыми. Фильтр по одному ключу
не меняет суммарный расход модели в её заголовке.

Этот раздел показывает локальные Gemini RPD за сутки **Pacific Time**. Выбор
периода Workload его не меняет. Резервирование квоты, отправка API-запроса и
готовый ответ — разные события. Неизвестный расход/предел отмечается отдельно;
отсутствие данных не означает нулевой расход. Допуск по локальному лимиту не
доказывает доступность модели у провайдера.

## Остальные показатели

**Avg Response** использует последние 1 000 завершённых операций текущего
процесса. **Error Rate** и **Cache Hit Rate** используют историю предыдущих
30 дней, загруженную при запуске, вместе с новыми событиями процесса. Они не
меняются при выборе периода Workload и не являются отдельным скользящим
календарным отчётом. Обработанные ошибки генерации передаются владельцу
операции, даже если пользователю уже показан текст ошибки без исключения.

Старые поля JSON `/api/overview`, SSE и Prometheus остаются для совместимости;
новые календарные карточки читают только `metrics.traffic`. Недоступный снимок
не подтверждает исправность сервисов, а успешный `/health` не доказывает
доступ к Telegram или внешней модели.
