# 🔍 Анализ целесообразности механизма ротации ключей при ошибках

## 📋 Текущая ситуация

### Как работает сейчас:

1. **Выбор ключа** (`app/handlers/agent.py`):
   - Перед запросом вызывается `_resolve_ai_request()` → `get_available_gemini_key()`
   - Выбирается один ключ на основе наименьшего использования (quota)
   - Ключ передается в `get_gemini_response()` или `get_openrouter_response()`

2. **Обработка ошибок** (`app/services.py`):
   - При ошибке API (quota, invalid key, 503, etc.) возвращается ошибка пользователю
   - Есть retry механизм для 503 ошибок, но **использует ТОТ ЖЕ ключ**
   - Ключи помечаются как "исчерпанные" только на основе количества запросов (quota), **не на основе ошибок**

3. **Проблема "Хрустального запроса":**
   - Пользователь пишет сообщение → Бот берет ключ А → Ключ А выдает ошибку (например, quota exceeded или invalid key)
   - Бот падает с ошибкой → Пользователь видит "🚫 Достигнут лимит запросов к API" или "❌ Произошла ошибка"
   - **Даже если ключ Б доступен и работает, он не используется**

---

## ✅ Предложенное решение

### Механизм Retry с ротацией ключей:

```
Попробуй Ключ А → Ошибка? 
→ Пометь Ключ А как плохой (для определенных типов ошибок)
→ Попробуй Ключ Б → Успех? 
→ Отдай ответ пользователю
```

**Пользователь даже не узнает, что первый ключ сбойнул.**

## 🎯 Оценка целесообразности

### ✅ **ПЛЮСЫ:**

1. **Улучшение UX:**
   - Пользователь не видит ошибку, если другой ключ работает
   - Автоматическое переключение между ключами
   - Повышение надежности системы

2. **Автоматизация:**
   - Не нужно ручное вмешательство администратора
   - Система сама адаптируется к проблемам с ключами
   - Снижение нагрузки на поддержку

3. **Логичность:**
   - Если один ключ не работает (quota exceeded, invalid key), логично попробовать другой
   - Это стандартная практика в enterprise системах

---

### ⚠️ **МИНУСЫ И ПРОБЛЕМЫ:**

#### 1. **Критично: Различение типов ошибок**

**НЕ ВСЕ ОШИБКИ означают "плохой ключ":**

| Тип ошибки | Означает | Действие |
|-----------|----------|----------|
| **Quota Exceeded** | Ключ валиден, но исчерпан лимит | ✅ Попробовать другой ключ |
| **Invalid API Key** | Ключ невалиден/отозван | ✅ Попробовать другой ключ |
| **Authentication Error** | Проблема с авторизацией | ✅ Попробовать другой ключ |
| **503 Service Unavailable** | Проблема сервера, не ключа | ❌ НЕ менять ключ (текущий retry правильный) |
| **Timeout** | Проблема сети/сервера, не ключа | ❌ НЕ менять ключ |
| **Rate Limit** | Ключ валиден, но превышен лимит запросов/сек | ⚠️ Попробовать другой ключ ИЛИ подождать |
| **Invalid Request** | Ошибка в запросе, не ключа | ❌ НЕ менять ключ (это ошибка в коде) |

**Вывод:** Нужна функция `should_retry_with_different_key(error)` для определения, нужно ли пробовать другой ключ.

#### 2. **Архитектурные изменения**

**Текущая архитектура:**
```python
# В app/handlers/agent.py
key = await db.get_available_gemini_key(model)
response = await services.get_gemini_response(key['api_key'], ...)
```

**Предложенная архитектура требует:**
- Обертку вокруг `get_gemini_response()` в `app/handlers/agent.py`
- Или изменение `get_gemini_response()` для поддержки ротации ключей
- Механизм пометки ключей как "проблемных" (временная пометка в памяти или БД)

#### 3. **Механизм пометки "плохих" ключей**

**Варианты реализации:**

**A. Временная пометка в памяти (Рекомендуется):**
- Set проблемных ключей в памяти на время запроса/сессии
- Не сохранять в БД (ключи могут восстановиться)
- Простое решение, но теряется при перезапуске

**B. Пометка в БД:**
- Таблица `failed_keys` или поле `is_failed` в `api_keys`
- Требует изменения схемы БД
- Более сложное, но персистентное

**C. Использование существующей системы quota:**
- Увеличивать счетчик использования для проблемных ключей до лимита
- Хак, но работает с текущей архитектурой
- Не рекомендуется: искажает статистику

#### 4. **Ограничение количества попыток**

- Нельзя пробовать все ключи бесконечно
- Максимум 2-3 ключа на запрос (иначе задержка для пользователя)
- После 2-3 неудач показать ошибку пользователю

#### 5. **Проблема с quota exceeded**

**Текущая логика:**
- `get_available_gemini_key()` выбирает ключ с наименьшим использованием
- Но если ВСЕ ключи близки к лимиту, может быть выбрано несколько ключей с quota exceeded подряд

**Решение:**
- Улучшить `get_available_gemini_key()` для более точного определения доступности
- Или увеличить threshold (сейчас используется `LIMIT_THRESHOLD_PERCENT`)

   - Quota Exceeded

   - Rate Limit (опционально)

2. **Временная пометка проблемных ключей в памяти:**
   - Set проблемных ключей на время обработки запроса
   - Использовать `asyncio` локальные переменные или глобальный dict с TTL
   - Не сохранять в БД (ключи могут восстановиться)

3. **Лимит попыток:**
   - Максимум 2-3 ключа на запрос
   - После неудачи показать ошибку

4. **Функция определения типа ошибки:**
   ```python
   def should_retry_with_different_key(error: Exception) -> bool:
       """Определяет, нужно ли пробовать другой ключ при этой ошибке."""
       error_msg = str(error).lower()
       
       # Ошибки, связанные с ключом - пробуем другой
       if any(x in error_msg for x in ["quota", "invalid api key", "authentication", "unauthorized"]):
           return True
       
       # Ошибки сервера/сети - НЕ меняем ключ
       if any(x in error_msg for x in ["503", "unavailable", "timeout", "invalid request"]):
           return False
       
       return False  # По умолчанию не меняем
   ```

### ❌ **НЕ РЕКОМЕНДУЕТСЯ:**

1. Менять ключ при 503/Timestamp ошибках (это проблемы сервера, не ключа)
2. Сохранять пометку "плохих" ключей в БД (ключи могут восстановиться)
3. Пробовать больше 3 ключей (задержка для пользователя)

## 🔧 Предлагаемая архитектура

### Вариант 1: Обертка в `app/handlers/agent.py` (Рекомендуется)

```python
async def _get_ai_response_with_key_rotation(
    model_name: str,
    history: list,
    system_instruction: str = None,
    user_id: int = None,
    chat_id: int = None,
    use_openrouter: bool = None,
    max_key_retries: int = 3
):
    """Получает ответ от AI с автоматической ротацией ключей при ошибках."""
    
    failed_keys = set()  # Временная пометка проблемных ключей
    
    for attempt in range(max_key_retries):
        # Получаем ключ, исключая проблемные
        key_data, model_used, resolution = await _resolve_ai_request_with_exclusion(
            model_name, 
            failed_keys,
            use_openrouter
        )
        
        if not key_data:
            return "🚫 Все ключи недоступны. Попробуйте позже.", None
        
        # Пробуем запрос
        response_text, token_count = await _get_ai_response(
            key_data['api_key'],
            history,
            model_used,
            system_instruction,
            user_id,
            chat_id,
            use_openrouter
        )
        
        # Проверяем, является ли ответ ошибкой, связанной с ключом
        if response_text and is_key_related_error(response_text):
            failed_keys.add(key_data['key_hash'])
            logging.warning(f"Key {key_data['key_hash'][:8]}... failed, trying next key")
            continue  # Пробуем следующий ключ
        
        # Успех или ошибка, не связанная с ключом
        if response_text and not is_error_message(response_text):
            # Успех - инкрементируем использование
            await _increment_key_usage(key_data['key_hash'], model_used, use_openrouter)
        
        return response_text, token_count
    
    # Все ключи не сработали
    return "🚫 Все доступные ключи не сработали. Попробуйте позже.", None
```
