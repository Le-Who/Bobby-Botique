## 2024-05-18 - Missing ARIA States on Custom Navigation Tabs
**Learning:** Found a recurring pattern where custom-built tab navigations (like the one in `dashboard.html`) only toggle visual states (e.g., CSS `.active` classes) without signaling state changes to screen readers via `aria-selected` and `aria-controls` properties, preventing users from tracking active tabs correctly.
**Action:** When building custom tab components or enhancing existing ones, ensure the parent element has `role="tablist"`, each child button has `role="tab"`, and Javascript click handlers toggle `aria-selected` attributes identically to the visual classes. Add `role="tabpanel"` to the corresponding panel elements.
## 2024-05-28 - Explicit WAI-ARIA mappings for custom tabs and dynamic counters
**Learning:** For robust accessibility in custom dashboard tab navigation, implicitly pairing `aria-controls` on buttons to `id` on panels is not enough. The `role="tabpanel"` elements must explicitly link back to the tab buttons using `aria-labelledby`, ensuring screen readers announce the correct tab context when focus enters the panel content. Additionally, visual dynamic badges (like error counters) updating via JS need `aria-live="polite"` to be reliably announced as their content changes without a page refresh.
**Action:** Always implement bidirectional linking for custom tabs (`aria-controls` on the tab button pointing to the panel `id`, and `aria-labelledby` on the panel pointing to the tab button `id`). For any dynamically updated element like a notification badge or counter, ensure `aria-live="polite"` (or `"assertive"` if critical) is applied so background DOM updates are exposed to assistive technologies.
