## 2024-07-03 - Mitigate SSRF with Robust DNS Validation
**Vulnerability:** The application was vulnerable to Server-Side Request Forgery (SSRF). The URL sanitization logic in `InputSanitizer.sanitize_url` relied on a naive `hostname.lower() == "localhost"` string comparison and basic `ipaddress.ip_address(hostname)` checks. This failed to account for URLs containing hostnames that resolve to internal/private IP addresses (e.g., local DNS rebinding attacks, wildcards like `127.0.0.1.nip.io`, or custom internal domains), allowing attackers to bypass the check and force the server to make arbitrary internal requests.
**Learning:** Checking only the string representation of a URL's hostname is insufficient. An attacker can provide a valid-looking hostname that DNS resolves to a private or loopback IP address. To properly secure URL validation against SSRF, the hostname must be actively resolved via DNS and all associated IPs must be checked against private/internal IP ranges using `ipaddress`.
**Prevention:** Always use `socket.getaddrinfo(hostname, None)` to resolve hostnames before trusting external URLs. Verify all returned IP addresses (both IPv4 and IPv6) to ensure they are not loopback (`is_loopback`), private (`is_private`), link-local (`is_link_local`), multicast (`is_multicast`), or unspecified (`is_unspecified`). Never rely solely on string matching (like "localhost") to block internal traffic.
